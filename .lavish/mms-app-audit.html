P1F01Fixed · regression passed

GPS maps enter an endless render loop

The shared map repeatedly sets a new center tuple from a freshly filtered array. The latest browser check recorded 91 copies of “Maximum update depth exceeded”. Dashboard and GPS Map both use this component.

Repair: GPS filtering is memoized; coordinate-equivalent center updates are skipped. Both map views pass the render-loop regression.

Original trigger, source and proposed repair
Trigger
Open Dashboard or GPS Map while at least one valid GPS point exists.
Source at audit revision 9975813
apps/web/src/components/shared/vehicle-map/index.tsx:164
Suggested fix
Memoize the filtered GPS data and skip center updates when coordinates have not changed.
P1F02Fixed · regression passed

One driver can depart on two vehicles at once

Both departure requests returned HTTP 200. Both tickets became in_progress. Departure claims the vehicle but does not claim the driver or check another active outing.

Repair: Active outings claim their driver under a consistent row lock. A second departure with that driver returns a conflict.

Original trigger, source and proposed repair
Trigger
Approve two adjacent trips today for the same driver on different vehicles. Check both out before either returns.
Source at audit revision 9975813
apps/api/src/modules/trip-tickets/transitions.ts:353
Suggested fix
Atomically claim both vehicle and driver at departure, reject active outings and inactive drivers, and release the driver at arrival.

Implementation decisions

Review decisions and accepted limits

  • Ruling: User instruction to fix the already reviewed audit accepts its suggested repairs; do not request another approval for the same scope — prior scope and fix recommendations were concrete — risk if wrong: user may prefer a different implementation and can review/revise the resulting diff.

  • Ruling: Complete each preventive task as one canonical preventive service-history row, advance the odometer atomically, and reject backwards readings — existing UI records individual completed tasks with no service-visit grouping — risk if wrong: several tasks at one visit count as several history entries, requiring a later grouping design.

  • Ruling: Use active outings plus consistent driver row locking as the gate claim; do not automatically change Driver.status to on_trip — future nonoverlapping booking must continue to work — risk if wrong: driver roster status remains a manual administrative attribute, while active trip records remain the operational truth.

  • Ruling: Apply reviewed patches to the original checkout without merging or changing its branch, after git apply --check — user wants the currently running local app fixed; managed worktree provides isolation/review — risk if wrong: concurrent user edits could conflict, requiring a normal conflict resolution rather than overwriting them.

  • Ruling: Retain expected existing test diagnostics rather than expanding this repair into unrelated logger/config cleanup — reviewers marked this Minor and the baseline had the same warnings — risk if wrong: noisy output can obscure a future failure; test exit codes and assertions remain authoritative.

  • Ruling: Do not backfill historical preventive rows in this repair — the accepted fix changes the completion transaction and no trustworthy historical grouping/backfill was specified — risk if wrong: older omitted history remains incomplete until a separately designed backfill.

  • Ruling: Preserve the accepted per-task preventive model without adding service-visit grouping or a new global idempotency protocol — recurring tasks already use individual completion records — risk if wrong: duplicate operator submissions need a separate workflow design.

  • Ruling: Keep the authorized complete-list queue solution without a new server-pagination or fleet-load redesign — real regressions verify the reported boundary beyond 100 records — risk if wrong: very large installations may later require measured pagination work.

  • Ruling: Do not rewrite unrelated existing approval/cancellation, duplicate-note or spare-part races without a concrete in-scope regression — the user approved the sixteen audited repairs — risk if wrong: untested older variants may still need a subsequent audit. The newly introduced FK deadlock is in scope and must be fixed now.

  • Ruling: Preserve existing administrator vehicle status/mileage overrides — changing that policy was not requested — risk if wrong: operator misuse can still create inconsistent manual records.

  • Ruling: Preserve browser-local scheduling policy and verify Manila conversions, without a product-wide timezone redesign — the current app and user operate with these semantics — risk if wrong: other regional deployments may require an explicit timezone policy.

  • Ruling: Use execution logs, isolated-service metadata and final original-database read checks for provenance — a read-only code review cannot independently reconstruct historical test execution — risk if wrong: those artifacts cannot prove every past write, so report the actual checks without claiming absolute forensic proof.

  • Ruling: Complete original-checkout patch application, live web/API/gateway checks and artifact update after the corrected final gate — these are still required controller tasks, not exclusions from the user request — risk if wrong: a worktree-only repair would leave the user's running app unfixed.
